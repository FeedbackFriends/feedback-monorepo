# iOS localization conventions

Established on 2026-11-04. The iOS localization implementation is complete; use these conventions for ongoing changes. See [implementation usage and verification limits](../ios-app/Docs/localization.md).

## Ownership and language

- The single editable source for app translations is the existing `ios-app/Modules/Sources/Localization` module. Use string catalogs in its resources and the public interface generated by XCStrings Tool. `L10n` retains only locale selection and formatting.
- Supported shipping languages: Danish (`da`) and English (`en`). Danish remains the source/development language. Use native Xcode String Catalog and Foundation preference matching and fallback. Explicit unsupported resource locales may fall back to English through Foundation; do not add a custom fallback registry. Formatting helpers follow the bundle-selected language locale and preserve the user’s time zone.
- Use `Bundle.module` for lookup and its native `preferredLocalizations` for the app formatting/SwiftUI locale. Adding a language means catalog translations and app localization configuration, with no custom language enum/registry or manual `.lproj` lookup. No custom language picker in this migration.
- Resolve module strings from the module's resource bundle. Main-app resources needed for notifications/system presentation must be derived from the same editable source; preserve the native linked-catalog packaging and verify notification delivery when changing its resources or payload contract.
- Localization uses Foundation; generated code also provides conditional SwiftUI conveniences. XCStrings Tool is a build-time dependency. It must not depend on Domain, Utility, DesignSystem, feature modules, or runtime SDKs. Those modules may depend on Localization as needed. Move formatting helpers out of Utility if retaining them there would create a cycle.
- Reducers retain dependency ownership under the existing TCA architecture. Localization does not introduce `@Dependency` in SwiftUI views.
- App-owned visible prose, including retained debug UI labels, belongs in localization resources. Logs, protocol/SDK identifiers, preview names, fixture IDs, URLs, and brand wordmarks are explicit exceptions.

## Terminology and copy

| Concept | Danish presentation | Rule |
| --- | --- | --- |
| Activity | aktivitet / aktiviteter | Preserve the current `Aktiviteter` navigation and activity/session distinction. Describe concrete meetings/workshops in explanatory copy. No product renaming in this migration. |
| Event | session / sessioner | One occurrence of an activity. Never expose the technical word `Event`. |
| Owner / Manager | mødeejer, or den ansvarlige where context fits | Keep code/API role names unchanged. |
| Participant | deltager / deltagere | Giving feedback remains account-free. |
| Feedback | feedback | Prefer `svar` or `feedbacksvar` when counting responses. |
| Question / template | spørgsmål / feedbackskabelon | App-owned template defaults are translated before copying into editable questions. |
| Rating | vurdering | Use `vurderingssvar` when distinguishing rating responses. Keep the existing numeric scale and score meaning. |
| Opinion | enighed | Helt uenig, Uenig, Neutral, Enig, Helt enig. |
| PIN | PIN-kode | Preserve leading zeros and the existing technical code value. |
| Profile / settings | Profil / Indstillinger | Sentence case; concise actions. |
| Email / location / duration | e-mail / lokation / varighed | Use `e-mailadresse` for an address. |
| Common actions | Gem, Annuller, Luk, Slet, Fortsæt, Næste, Tilbage, Prøv igen, Log ud, OK | Reuse only when the meaning is genuinely shared. |
| Missing optional profile field | Ikke angivet | Missing account data is not a failed search. |

Use plain Danish, short actionable error messages, and sentence case. Preserve brand names such as LetsGrow, Apple, Google, and Outlook. Keep code/API names stable. The optional `ios-app/CONTEXT.md` referenced by domain guidance does not currently exist; current iOS navigation and repository product-language guidance supply the terminology baseline.

## Keys and typed access

Use dot-separated semantic keys with lower-camel-case segments. Keys describe purpose, not source prose or a view type name. XCStrings Tool generates public camel-case members directly from the catalog; never maintain a duplicate Swift key enum or handwritten accessor list.

| Resource key | Swift resolved-string example | Parameters |
| --- | --- | --- |
| `common.save` | `String(appStrings: .commonSave)` | None |
| `profile.edit` | `String(appStrings: .profileEdit)` | None |
| `errors.invalidPin.message` | `String(appStrings: .errorsInvalidPinMessage)` | None |
| `activity.sessionCount` | `String(appStrings: .activitySessionCount(count))` | `Int` |
| `feedback.questionProgress` | `String(appStrings: .feedbackQuestionProgress(current, total))` | Two `Int` values |
| `session.invite.message` | `String(appStrings: .sessionInviteMessage(title, pinCode, link))` | Three verbatim `String` values |

Use `LocalizedStringResource(appStrings:)` or `Text(appStrings:)` when appropriate. Build in Xcode after editing the catalog so generated signatures and code completion are current. Explicit plural substitutions produce named parameters; other arguments use generated positional parameters. See the [adding-string workflow](../ios-app/Docs/localization.md#adding-a-string).

- Feature callers receive already localized strings, including for TCA `TextState`. Do not reinterpret a resolved string as a localization key in SwiftUI.
- Use `Int` counts and the generated parameter labels; never pass a preformatted count to choose a plural form. Use `Date`/numeric input in formatting helpers. PINs are strings; URLs are not translated.
- Give catalog entries translator comments explaining context, parameter meanings, units, and verbatim user content. Document positional placeholder order where the catalog format requires it.
- Translate complete sentences, including multiline sharing/support-email messages. Parameter order may vary by language. Avoid assembling grammatical sentence fragments.
- Keep empty text-field values and hidden technical identifiers outside the catalog. Static numeric scale endpoints can remain numeric UI values; their surrounding labels and accessibility descriptions must be localized.
- Use stable enum/ID values for logic and identity. Replace `section.title == "Aktuelt"` before localizing section headings; do not replace it with comparison to a translated string.

## Plurals and formatting

- Define singular/other forms for counts even when the Danish noun is identical: `1 svar` / `2 svar`, `1 spørgsmål` / `2 spørgsmål`, `1 session` / `2 sessioner`, `1 time` / `2 timer`. Handle zero deliberately, including existing empty states.
- New-response copy needs whole-sentence agreement, e.g. `Du har modtaget 1 nyt feedbacksvar …` / `Du har modtaget 2 nye feedbacksvar …`.
- APNs is an external contract: its existing feedback-received count and session title are both string arguments. Preserve `%1$@` / `%2$@` and use wording that agrees with all counts (`Du har modtaget … feedbacksvar …`). Do not introduce a numeric plural argument without a separate payload-contract change. Notification source lives in `Localization/AppBundleResources/Localizable.xcstrings`; the main-app path is a link compiled by Xcode. See the current [packaging status](../ios-app/Docs/localization.md#notification-and-system-string-packaging) before shipping.
- Use locale-aware decimals, percentages, dates, intervals, relative dates, and durations. A score such as 4.5 displays as `4,5` in Danish. Do not modify stored values, calculations, UTC instants, or the user's time zone.
- Preserve PIN formatting, URLs, user-authored questions, event titles, comments, account details, and calendar text verbatim. Do not treat them as translation keys.
- Template defaults become ordinary user data when selected/saved; later language changes must not rewrite persisted questions.

## Error mapping

Prefer a complete, nonblank pair of backend `userTitle`/`userMessage` fields for API failures, rendered as plain text. The [API error-copy contract](api-error-copy.md) owns language negotiation, backend translations and compatibility. Retain app-owned mappings for the six existing domain codes, HTTP failures and older/incomplete API responses. Transport failures, authentication SDK codes and known local errors remain client-localized. Never display diagnostic API `message`, `localizedDescription`, or NSError description text as production copy.

Keep technical details in diagnostics and preserve existing cancellation/retry behavior. New business-error wording belongs in backend Danish/English catalogs; local recovery and compatibility strings remain in the existing Localization module.

## External UI and documented exceptions

| Surface and current boundary | Migration responsibility |
| --- | --- |
| Apple authorization sheet (`FirebaseService` / `AppleLogin`) | Localize app-owned entry actions and errors. Current code sets requested scopes/nonce, with no explicit language override; system sheet wording remains platform-owned. |
| Google sign-in (`FirebaseService`) | Localize app-owned entry actions and errors. Current code configures client ID and presentation; check supported SDK language behavior during implementation without inventing an unsupported override. |
| Notification authorization (`NotificationClientLive`) | Localize app-owned explanations; the native authorization dialog is system-owned. Check app/default-language configuration and app display name. |
| Share sheet (`InviteView`, `ShareLink`) | Localize supplied messages and app labels. Native destinations/actions belong to the OS or receiving app. |
| Mail app launched by `MoreSection` | Localize subjects, placeholder instructions, and device-info heading supplied by LetsGrow. Mail app chrome and raw device values are external/diagnostic. |
| DatePicker and native controls | Supply the app-selected locale and localized labels; verify Danish control/accessibility presentation during iOS QA. |
| Settings, App Store, hosted privacy policy | Localize outgoing app-owned link labels. Destination UI/content is outside this iOS-only task. |

System/third-party UI may follow device or provider language policy. Record what actual QA shows; the Danish guarantee applies to LetsGrow-owned text.

## Validation policy

Keep [the source inventory](ios-localization-inventory.md) consistent when changing ownership or exceptions. Validate both source catalogs and compiled notification resources, and run the direct-copy guard with its narrow reviewed allowances. Verify changed grammar/parameters in resource tests and relevant Danish/English layouts through the existing visual workflow. Notification payload or packaging changes need their relevant delivery checks; see [current implementation and verification](../ios-app/Docs/localization.md#completion-and-verification).
